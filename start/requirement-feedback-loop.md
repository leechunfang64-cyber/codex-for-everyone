# AI 编程不是魔法，本质是需求拆解 + 反馈迭代

Codex 的工作质量，主要取决于你给它的目标、上下文和反馈。需求越模糊，它越容易用表面正确的代码掩盖真实问题。

## 需求拆解

一个可执行需求至少包含六个要素：

| 要素 | 问题 |
| --- | --- |
| 用户 | 谁会用这个东西 |
| 场景 | 在什么情况下用 |
| 输入 | 用户提供什么 |
| 输出 | 系统交付什么 |
| 规则 | 哪些行为必须稳定 |
| 验收 | 怎么证明它完成了 |

缺少验收标准时，Codex 很容易把“写完”当成“完成”。

## 反馈迭代

反馈不是说“还是不行”，而是给出可复现材料：

- 我执行了什么命令。
- 实际输出是什么。
- 预期输出是什么。
- 哪个文件、哪一行、哪个页面异常。
- 是否能稳定复现。

好的反馈会让 Codex 缩小搜索范围。坏的反馈会让它在错误方向上继续生成。

## 推荐提示词

```text
请先不要改代码。先阅读项目结构和相关文件，说明你理解的需求、影响范围、可能风险和验证方式。确认后再分步骤实现。
```

```text
这是报错输出。请不要直接猜原因，先根据日志列出 3 个最可能根因，说明每个根因如何验证，再执行最小修复。
```

```text
功能已经跑通。请把本次实现沉淀成 README 使用说明、常见问题和下一次可复用的提示词模板。
```

## 结构化迭代

1. 先做最小版本。
2. 跑通一条主路径。
3. 补失败场景。
4. 增加日志和错误提示。
5. 再考虑界面和体验。

这个顺序能保护现金流。过早做漂亮界面，会让你在需求还没验证时增加沉没成本。
